# SureStock — Progress

Status as of 2026-08-22. **Backend Phase 3 (Selling) is done for everything backend-shaped in it** — T-16, T-18, T-19, T-20 — and now includes several App Flow-driven additions beyond T-19's own stated criteria: `GET /sales` (page-number pagination), `GET /sales/stats`, `GET /sales/export`, `GET /till-shifts`, `GET /products/popular`, `GET /products/recent` — plus a real correctness fix (cart-discount proration into refunds) found while building the frontend. Frontend build-sequence stages 1 through 4 are done and fully verified live; the T-19 refunds UI is built and verified; and the Sales, Sell, and now Reports screens have all been built/redesigned against user-supplied reference mockups — Sales into a full transactions+till-shifts dashboard, Sell into a category/browse grid with held carts, Reports into a full live-computed analytics page (profit, period comparisons, top/low sellers, inventory value) — all verified live against the real backend and database. This file is the handoff record for both halves: what's built, what's designed-but-not-built, and what's next either way.

Backend stack: Node.js + TypeScript, Fastify 5, Prisma 7 (no-rust-engine client, `@prisma/adapter-mariadb`), MariaDB 10.4. Frontend stack (decided, not yet built): React 18 + TypeScript, Vite, Tailwind, TanStack Query, Zustand, React Router, React Hook Form + Zod, Dexie — see the Frontend section below. Full reasoning for every decision lives in the six planning docs (`Document request form/`) and the two published artifacts (**Backend Integration Blueprint**, **SureStock Frontend Blueprint**) referenced throughout; this file tracks *status*, not design rationale.

## Done

### Phase 0 — Foundations
- **T-01 Repository, tooling.** npm workspaces monorepo (`apps/SureStock-backend`), TypeScript strict mode, ESLint 9 flat config, Vitest, Fastify app/server split (`app.ts` buildable without binding a port, for fast `.inject()`-based tests).
- **T-02 Database and migrations.** Full schema from Doc 5 translated to MariaDB (21 tables). Two Postgres-only features substituted: `pg_trgm` → plain MariaDB `FULLTEXT` (not typo-tolerant — see T-07 below for how that gap was actually closed), partial index → composite index. `stock_movement` append-only enforcement implemented as `BEFORE UPDATE`/`BEFORE DELETE` triggers (a MySQL/MariaDB privilege-model constraint ruled out the originally-planned `REVOKE`-based approach — privileges there are additive-only, confirmed empirically). Least-privilege runtime DB user, separate migration-only user. Migration history (7 migrations) verified to replay cleanly on a from-scratch database.
- **T-03 Auth and roles.** JWT access + refresh tokens, PIN quick-switch with 5-attempt/5-minute lockout (tracked in the database, not memory), server-side RBAC (`app.authenticate` / `app.requireRole`) reused by every module since. Deactivating a user takes effect on their next request, not just at token expiry.

### Phase 1 — Catalogue
- **T-05 Categories and suppliers CRUD.** Full CRUD, archive/restore, and a guarded hard-delete (409 if still referenced by a product — backed by a database-level `RESTRICT` foreign key, not just an application check).
- **T-06 Product and variant CRUD.** Product+variant creation in one transaction; opening stock posts as a real `OPENING_BALANCE` movement, never a direct write to the cached quantity. Cost price is hidden from cashiers in the API response itself. Selling-price changes write a `price_history` row and require a reason. Duplicate SKU/barcode rejected with a specific message (required reverse-engineering the actual error shape this Prisma/MariaDB combination produces — it doesn't match Prisma's documented format).
- **T-07 Product search and list.** Category/status/stock-level filters (combinable), cursor-based pagination (proven not to skip/duplicate rows under concurrent writes, not just assumed), and application-side fuzzy search closing the typo-tolerance gap MariaDB's FULLTEXT can't fill. Required two rounds of real performance work to hit the 150ms/5,000-row target — profiled properly rather than guessed; the fix was moving the candidate-fetch query to raw SQL, since Prisma's query-builder overhead (not MariaDB or the driver) was the actual bottleneck.
- **T-08 Spreadsheet import.** CSV and XLSX, fuzzy column-mapping suggestions, preview with per-row validation reasons, all-or-nothing commit via bulk `createMany` (not per-row inserts — 1,000 rows commits in a few seconds against the 30-second target).

### Phase 2 — Inventory movement
Read the Backend Integration Blueprint's §07/§08 before touching anything here: the property-based ledger-invariant test it specifies (§08) is the actual proof this phase is built on, not a nice-to-have.

- **T-10 Stock movement ledger primitives.** The ledger table and its append-only triggers already existed (T-02); what T-10 built is `postMovement()` (`src/modules/inventory/movement.service.ts`) — the one function every stock-changing writer now calls, which inserts the `stock_movement` row *and* increments `product_variant.quantity_on_hand` inside the same passed-in transaction, so the two can never be written as separate, driftable steps. `product.service.ts`'s existing `OPENING_BALANCE` writer (T-06) was refactored to call it instead of hand-rolling the same two statements — the point of a shared primitive is retiring the duplication, not just being available for next time. **Property-based test** (`movement.test.ts`, using `fast-check`, added as a devDependency): 15 random sequences of up to 20 movements each, asserting ledger-sum equals `quantityOnHand` after *every single step*, not just at the end — the literal wording of Doc 6's acceptance criterion and the Blueprint's §08. Also added the one thing that was actually unverified before now despite being load-bearing everywhere: a direct test that `UPDATE`/`DELETE` on `stock_movement` throw, proving the T-02 triggers actually work rather than assuming it from the migration SQL.
- **T-11 Receive stock** (`POST /inventory/receive`, OWNER/MANAGER). Accepts multiple lines in one call, all committing as one transaction and sharing one generated `referenceId` so they read back as a single delivery. Moving-average cost: `(existingQty×existingCost + receivedQty×receivedCost) / (existingQty+receivedQty)`, existing quantity clamped to zero if it's currently zero or negative (no coherent cost basis to weight against otherwise) — verified against an exact worked example (20 units @ GH₵5.00 + 10 @ GH₵8.00 → GH₵6.00, not just a formula unit test). Perishable products (`product.isPerishable`) get a real `Batch` row every time (batch code auto-generated if not supplied, expiry captured when given); non-perishables never do. The response is deliberately complete (product/variant names, before/after cost, quantities, batch info) — that's the "goods-received summary" T-11 asks be printable; actually printing it is a frontend concern.
- **T-12 Manual adjustments** (`POST /inventory/adjustments`, OWNER/MANAGER only — explicitly not cashiers). Reason code is a deliberate subset of `MovementReason` — `DAMAGE`/`EXPIRY`/`THEFT`/`STOCK_TAKE_ADJUSTMENT` — since every other reason already has its own dedicated writer (a sale, a receipt, product creation). A note is required (schema-enforced, not just documented), and damage/expiry/theft are schema-rejected if given a positive delta — those are always a loss, only a stock-take recount can legitimately go either way. Every adjustment writes an `audit_log` row with real `before`/`after` JSON (`{quantityOnHand: ...}` before, `{quantityOnHand, quantityDelta, reasonCode, note, movementId}` after) sharing its own id with the movement's `referenceId`, so either record leads straight to the other.
- **T-13 Product detail: history, margin, days-of-cover.** New paginated, reason-filterable endpoint `GET /products/:id/variants/:variantId/movements` (same opaque-cursor design as T-07, newest-first, `occurredAt`+`id` tiebreaker since one T-11 receipt's lines all share an `occurredAt`). `GET /products/:id` now also returns `marginPercent` and `daysOfCover` per variant — gated behind the exact same cashier check as `costPrice`, since neither means anything without it. Days-of-cover is computed purely from the ledger's own `SALE`-reason movements over a trailing 30-day window (`quantityOnHand ÷ average daily SALE outflow`) — deliberately has no dependency on T-16 (the sale-write endpoint) existing yet, since the ledger doesn't care which task produced a movement; returns `null` (not `0` or `Infinity`) when there's no sales history to estimate from. "Stock on hand matches the ledger exactly" is directly asserted in `product-detail.test.ts` by independently re-summing `stock_movement` and comparing to what the detail endpoint actually returned, not just trusted from T-10's own test.

**Test suite (Phase 0-2)**: 60 integration tests, all against real MariaDB, stable across three consecutive full runs. One unrelated pre-existing test (`search.test.ts`'s 150ms performance budget) flaked under that session's system load — see Known Issues.

### Phase 3 — Selling (backend-shaped tasks only)
T-14 (cart/sell screen) and T-15 (barcode scanning) are frontend work with no backend gap — the cart is client-side state, and barcode lookup (`GET /products/lookup`) already existed from T-07. T-17 (receipts) needed nothing new either: `GET /sales/:id` already returns everything a receipt needs, "reprint reproduces the original exactly" falls out for free from `Sale`/`SaleLine`/`Payment` never being edited after creation, and SMS delivery has no provider/credentials configured anywhere in this project to build against — deferred honestly rather than faked, same as T-09's product photos. That left T-16, T-18, T-19, T-20 as the real backend scope, all in a new `src/modules/sales/`.

- **T-20 Till shifts** (`POST /till-shifts`, `GET /till-shifts/current`, `POST /till-shifts/:id/close`) — built first since `Sale.tillShiftId` is required, so nothing in T-16 works without it. One open shift per cashier (`userId`, no `locationId` on the model — implicitly location-scoped through the user). Closing computes `expectedCash = openingFloat + Σ(CASH ∪ CHANGE payments on this shift's sales)` — `CHANGE` has to be summed alongside `CASH`, not folded into it, because T-16 records change given back as its own negative `CHANGE`-method payment row rather than netting it into the `CASH` row (more auditable: "customer tendered GH₵50 cash, GH₵18 change given" survives as two rows, not one net figure). A variance past a hardcoded GH₵20 threshold (no Settings mechanism exists yet — T-29 — to make this configurable) writes a real `audit_log` entry, since there's no notification channel to actually deliver an alert through.
- **T-16 Payment and sale write** (`POST /sales`, `GET /sales/:id`) — the single most important transaction in the system, and every clause of its acceptance criteria is load-bearing, not decoration:
  - *Price/cost are never trusted from the client.* The request carries `variantId` + `quantity` (+ optional discount) per line, nothing else — `unitPrice`/`unitCost` are always the variant's live values, read inside the transaction (Doc 2 §3.3: "captured at that moment").
  - *Concurrency-safe.* Every variant touched is locked with a raw `SELECT ... FOR UPDATE`, in variant-id-sorted order (Doc 2 §3.1's deadlock-avoidance rule for two tills each locking multiple rows). Verified with a real test, not just reasoned about: two simultaneous `Promise.all` requests both buying the last unit of the same variant — re-ran in isolation 5 times, exactly one `201`/one `409` every time, stock lands on exactly `0`, never negative, never double-sold.
  - *Idempotent.* `Sale.id` is client-generated and the primary key; a duplicate `POST` (checked first as a fast-path read, then caught as a `P2002` fallback for the race where two duplicate requests arrive together) returns the existing sale rather than erroring or double-writing. Verified under both paths.
  - *Split tender and change.* Multiple `payments[]` entries, any combination of methods; overpayment on a cash tender produces a `CHANGE` payment row for exactly the excess; overpayment with no cash tender present is rejected (you can't hand back mobile-money change).
  - *Tax*, correctly handling `TaxRate.isInclusive` both ways (extracted from an inclusive price vs. added on top of an exclusive one) — nothing in the catalogue has a tax rate configured yet, but the arithmetic is right either way.
  - Online stock-availability check (this session's resolution of the "concurrent online stock races" open item from Phase 2, for the online path specifically): a line that would take `quantityOnHand` negative is rejected with `409` and the transaction rolls back cleanly — nothing partially commits. The offline half of that same decision (queued sales are accepted even negative, flagged for review) has nowhere to plug in yet since T-22 (offline outbox/sync) doesn't exist — left as an explicit note for whoever builds it, not guessed at now.
- **T-18 Discounts and manager override** — folded into T-16's request body (`lines[].discountAmount`, `cartDiscountAmount`), not a separate endpoint, matching the Engineering Plan's own framing of T-18 as a sequential extension of the sale write. A discount past a hardcoded 10%-of-gross threshold (same "no Settings mechanism yet" caveat as T-20's variance threshold) requires `managerOverride: {managerId, managerPin, reason}` in the request; the PIN is verified with the existing `verifyPin()` from T-03's auth module (already a standalone, reusable, non-route-private function) *before* the transaction opens, and the resolved manager's role is checked (`CASHIER` supplying valid credentials is still rejected — self-approval isn't approval). A `DISCOUNT_OVERRIDE` audit-log entry records both the cashier (`userId`) and the approving manager (`after.approvedBy`), per T-18's "logged with both users."
- **T-19 Refunds** (`POST /sales/:id/refund`) — a new linked `Sale` with `refundOfSaleId` set and negative amounts throughout, never an edit to the original (its `status` moves to `PARTIALLY_REFUNDED`/`REFUNDED` — the Backend Integration Blueprint's own walkthrough confirms that's expected, not a contradiction of "the original sale is unmodified," which is about its financial facts, not its state). Per-line `restock: true` posts a `REFUND` movement (stock returns); `restock: false` posts none (write-off). "Refunds cannot exceed what was sold" is enforced across *multiple* partial refunds of the same sale, tracked by summing prior refund lines' quantities per `variantId` (the schema has no direct FK from a refund line back to the specific original line, so this assumes one line per variant per sale — true for how a cart is expected to work). Same idempotency treatment as T-16. `GET /sales/:id` now also returns a `quantityRefunded` per line on any original (non-refund) sale, computed from prior refund lines — what a refund UI needs to bound its quantity input without guessing or relying on a 409 to find the limit.
- **Cart-discount proration fix, found and fixed 2026-08-20** while building the frontend refunds UI (below): a cart-level discount used to reduce only the sale's grand total, never any single line's own stored `lineTotal` — so refunding one line of a cart-discounted sale over-refunded it by that line's share of the discount (verified: a GH₵96/GH₵50-discount/GH₵46-paid sale refunded GH₵96, not GH₵46, when only one line was refunded). This was actually a documented, known gap in the original T-19 write-up, unreachable before now since no refund UI existed to trigger it. Fixed at the root: `createSale` now prorates `cartDiscountAmount` across every line's `lineTotal`/`discountAmount` at write time, using largest-remainder allocation in integer pesewas so the shares always sum back to exactly the cart discount, never off by a rounding pesewa. Every downstream reader (refunds, reports, receipts) sees the true post-discount amount for free. New test proves it directly: a two-line, differently-priced cart with a 10% cart discount, refund one line, assert the refunded amount is the prorated share, not the pre-discount price. All pre-existing tests (including the ones that only ever checked the sale-level total, never a line's own `lineTotal` after a cart discount) still pass — 87/87 stable.
- **`GET /sales`, added 2026-08-20** — not one of T-19's own acceptance criteria, but there was no way to find a sale to refund at all without it (Doc 3 App Flow §5: "a reverse-chronological list filterable by date, staff member, and payment method"). A `CASHIER` is always scoped to their own sales server-side regardless of what `userId` they pass — Doc 1's role table ("cashiers see their own transactions") enforced in the service layer, not just hidden in the UI. Filterable by `dateFrom`/`dateTo`/`userId`/`method` (method requires a `payments: {some: {...}}` join since a sale's tender lives on its `Payment` rows, not the `Sale` itself).
- **Sales screen redesign, 2026-08-20** — same day, after the user shared a reference mockup (`surestock-pages/sales.jpeg`, bold purple/indigo brand — same treatment as the earlier Inventory mockup) and asked for everything shown, not just a subset. Three more backend endpoints, all sharing `buildSalesWhere()` with `GET /sales` for identical filtering/cashier-scoping:
  - **`GET /sales` switched from keyset-cursor to page-number pagination** (`page`/`pageSize`, returns `totalCount`/`totalPages`) — deliberately different from T-07/T-13's cursor design, and deliberately safe to be different: sales are an append-only, insert-at-the-head log ordered newest-first, so a fixed older page never shifts under concurrent writes the way T-07's mutable, filterable product list could. The risk cursor pagination exists to avoid just doesn't apply to a chronological history — see the doc comment on `listSalesQuerySchema`. `GET /till-shifts` uses the same reasoning (a shift is opened once, closed at most once, then never touched again).
  - **`GET /sales/stats`** — the KPI cards' Total Sales/Transactions/Completed/Refunded figures plus a per-day trend for each (the sparklines). "Completed" vs. "Refunded" means `refundOfSaleId` null or not, *not* the `status` field — a refund row's own `status` is always `COMPLETED` (only the original sale's status moves to `REFUNDED`/`PARTIALLY_REFUNDED`), so `status` alone can't tell the two buckets apart. Defaults to a trailing-14-day window when no date filter is given (unlike the plain list, which stays unbounded so history keeps paging — a KPI trend is inherently period-shaped and wouldn't mean much unbounded).
  - **`GET /sales/export`** — plain CSV of every row matching the current filters (not just the current page), same filter/scoping logic as the list. No PDF export — that would be a new rendering dependency, a real decision to make deliberately rather than add unprompted, same category as camera barcode scanning.
  - **`GET /till-shifts`** — the Sales screen's "Till shifts" tab. `TillShift` has no `locationId` of its own (implicitly location-scoped through `user`, same as everywhere else this comes up), so scoping goes through the `user` relation; same cashier-sees-own-shifts-only rule as sales.
- **Sell screen quick-picks, added later the same day (2026-08-20)** for the Sell redesign below — `GET /products/popular` and `GET /products/recent`, both in `product.service.ts` (catalogue module, not sales — the response shape is a lightweight "sell tile," not a full `Sale`). Doc 3 App Flow §3 asks for "a grid of category tiles and favourite products" but never defines "favourite," so it's grounded in the one real signal that exists: `popular` ranks active variants by real units sold (`SUM` of `SALE`-reason `stock_movement` rows) over a trailing 30 days, optional `categoryId` filter, ties broken alphabetically so a fresh shop with no sales history still gets a stable, sensible order rather than random-looking results; `recent` returns the most recently sold distinct variants from real `sale_line` rows (excluding refund lines — a refund isn't a customer buying something). Both raw-SQL joins, same style as `createSale`'s locked-read query.

**Test suite (Phase 3)**: 23 new integration tests (4 for T-20, 13 for T-16/T-18, 6 for T-19) — 83 total across the whole backend. Stable across two full consecutive runs at 83/83 (the search-performance flake from Phase 2's writeup didn't recur once system load settled). **Updated 2026-08-20**: 4 more tests for the original `GET /sales` list + cart-discount proration fix, then 9 more for the Sales redesign (page-based pagination rewrite, stats, export, till-shifts list), then 2 more for `/products/popular`/`/products/recent` — 94 total, stable (the search-performance flake reappeared intermittently again this session, same known cause — see Known Issues).

## Reports screen — built 2026-08-22, against a third user-supplied reference mockup (`surestock-pages/reports.jpeg`)

A real discussion happened before any code, per the user's explicit request — worth recording since the resolved questions shape the whole implementation:

- **Live-computed, no rollup job.** The schema already has an unused `daily_summary` table (revenue/cogs/grossProfit/etc per day) — exactly what T-24's "daily rollup job" was meant to populate. Decided against building it: everything here is computed live off the real ledger on every request (same approach as `GET /sales/stats`), and `daily_summary` stays a documented future optimization if a real range ever gets slow at this shop's scale. No cron, no staleness, no backfill logic to maintain.
- **One page-level date range drives everything** (KPI cards, chart, tables) — the 7D/30D/3M/12M buttons are presets for that one range, not an independent chart-only control.
- **Filters = staff + payment method** (page-wide, matching the Sales screen's own filters) **plus a category filter scoped only to the two product tables** (a sale itself isn't scoped to one category, but "top sellers in Beverages" is a real, useful slice).
- **Export = one CSV, every section** — Summary, Sales Over Time, Sales By Payment Method, Top Selling Products, Low/Slow Moving Products — one button, matching the mockup, not a control per chart/table.

New backend module `src/modules/reports/` (Manager/Owner gated only — cost/profit figures are inherently on this screen, so there's no cashier-safe partial view, same boundary the nav already enforced):
- **`GET /reports/overview`** — Total Sales (net), Gross Profit, Transactions, Avg Order Value, Refunds, each with a vs-prior-equal-period % change (`null`, not a fabricated 0% or Infinity, when the prior period has nothing to compare against), plus the bottom stat row (out-of-stock/low-stock/total-product counts, inventory value, total purchased). "Transactions" here means completed sales only (`refundOfSaleId` null) — a refund gets its own dollar-figure card instead of inflating the count, a subtly different definition from the Sales screen's own "Transactions" KPI, which counts every row.
- **`GET /reports/trend`**, **`GET /reports/payment-breakdown`** — the chart data. `CHANGE` payments are folded into the `CASH` bucket, not shown as their own category or dropped — a real bug caught mid-build: dropping `CHANGE` outright left `CASH` overstated by however much change was given back; the fix mirrors till-shift.service.ts's own existing convention ("both have to count toward the cash drawer").
- **`GET /reports/products?direction=top|low`** — one query, sort flipped, for both the Top Sellers and Low/Slow Movers tables (they're the same ranking, not two concepts). Refund lines are excluded outright, so a refund never erases a product's real sales history from the ranking.

Per the user's explicit "let's go backend first," this covers the backend half of all three offline tasks (T-21/T-22/T-23) — the frontend halves (PWA shell/service worker, IndexedDB outbox, review-queue UI) are not built this pass. A short scoping round (AskUserQuestion) resolved three real forks before coding: build all three backend halves together in one pass, since T-22 without T-23 has nowhere to put a flagged sale; `GET /sync/catalogue?since=` excludes live `quantityOnHand` (stock changes on nearly every sale, and Doc 2's own model already accepts stock is allowed to be wrong offline — shipping a number that's stale the instant it's cached would be a confidently-wrong lie, not a useful one); the review queue (T-23) is a genuinely new table, not audit_log extended with resolution columns, since audit_log is documented everywhere else as pure append-only history with no workflow state.

**Schema**: new `ReviewQueueItem` model (`review_queue_item`) — `type` (`NEGATIVE_STOCK` | `SYNC_VALIDATION_FAILURE`), nullable `saleId`/`variantId` references, `reason`, a `details` JSON blob, and real resolution state (`resolvedAt`/`resolvedBy`/`resolutionNote`) — the actual reason it's a new table and not audit_log. `Sale` already had unused `syncedAt`/`deviceId` columns sitting in the schema from an earlier pass, now finally populated. `createSaleBodySchema` gained an optional `soldAt` — Doc 2 is explicit ("server time is authoritative for reporting; device time is retained for forensics") that an offline sale should report as having happened when the device's own clock says, not whenever the batch happened to replay; never sent by the online Sell screen, only by sync.

**`createSale()` (T-16) gained a non-breaking `options` parameter** (`{ allowNegativeStock?, syncedAt? }`), defaulting to today's exact online behavior unchanged (verified: all 19 pre-existing `sale.test.ts` tests still pass untouched). When `allowNegativeStock` is set, a line that would take stock negative no longer throws — it's recorded and, once the sale commits, a `NEGATIVE_STOCK` review-queue row is written in the *same transaction* as the sale (Doc 2: "the server accepts the sale — it happened," and the flag can never disagree with the fact it describes, matching this codebase's "everything commits together" discipline everywhere else).

New module `src/modules/sync/`:
- **`GET /sync/catalogue`** (`since` optional — omitted means a full pull, the device's first-ever sync or a cache-clear). A product is included whenever *either* its own fields changed *or* any of its variants did — checking only `Product.updatedAt` would silently miss a price-only edit (by far the most common catalogue change), since that only bumps the variant's own `updatedAt`, never its parent's. Verified directly with a real test that edits only a variant's price and confirms the delta still includes the product. Cost price stays cashier-hidden, same rule as everywhere else it's returned; quantity/reorder fields are omitted entirely per the resolved scope above.
- **`POST /sync/batch`** (`{ sales: CreateSaleBody[] }`, reusing T-16's exact body shape). Each sale gets its own `createSale()` call — deliberately not all-or-nothing, so one bad sale ten items into an offline device's outbox doesn't sink the other nineteen. Only a well-formed `HttpError` (a real business-rule rejection) gets caught and turned into a `SYNC_VALIDATION_FAILURE` review-queue entry (with the raw attempted sale body preserved in `details`, since nobody was present to react live when the device reconnected hours later); any other error is left to propagate, so a genuine infrastructure fault surfaces as a real failure and the device's outbox correctly keeps retrying instead of a transient glitch getting silently relabeled as "needs a human decision." A duplicate sale id (already synced) is idempotent-transparent, same as `POST /sales`.

New module `src/modules/review-queue/` (T-23) — `GET /review-queue` (Manager/Owner, defaults to open items only — a review queue is meant to be worked down to zero, not paged through as history) and `POST /review-queue/:id/resolve` (records `resolvedBy`/`resolvedAt`/a required note; 409 if already resolved).

## T-27 Stock take — backend built 2026-08-23, on explicit "finish [it as] solid backend [work]" instruction

Grounded in Doc 3 App Flow §4.2 before writing anything: "Inventory → Stock take → choose full shop or a category. The system freezes an expected-quantity snapshot and presents a count list... Counted lines show a live variance. At the end a review screen lists only the discrepancies, sorted by value impact, each requiring a reason before posting. Posting writes adjustment movements and closes the stock take, which then becomes a permanent, uneditable record." T-27's own acceptance criteria add: "progress survives interruption... sales during a count are handled correctly."

**The one real design decision this task turns on**: `expectedQuantity` is genuinely frozen at count-start (matching the doc's own wording and the schema's stored column) and used for the *review-time* variance shown to the counter — but that frozen number must **never** be what actually gets posted to the ledger. Between count-start and posting, real stock-changing events (a sale, a delivery) can and do happen legitimately, and posting `counted − frozen-snapshot` would silently re-undo them. Instead, every counted line is re-locked (`FOR UPDATE`) and adjusted against its **live** `quantityOnHand` at the moment of posting — whatever happened in between is already correctly reflected there, so the adjustment brings the ledger to exactly the counted number regardless of what moved it. This is "sales during a count are handled correctly," implemented as a real, load-bearing distinction rather than an afterthought: the stored `variance`/`varianceValue` stay the honest review-time story (counted vs. original expectation), while the actual posted delta is a separate, correct computation the service never conflates with it.

**Schema**: Doc 5's own field list for `stock_take` never actually included a `category_id` column despite Doc 3 requiring category-scoped counts — added it (nullable, only set when `scope = CATEGORY`), plus a `@@unique([stockTakeId, variantId])` guard so a variant can never appear twice on one count's line list.

New module `src/modules/stock-take/` (Manager/Owner-gated, matching Doc 3's own role table for this screen):
- **`POST /stock-takes`** — one `IN_PROGRESS` stock take per location at a time (same "one active thing" rule as `TillShift`). Snapshots `expectedQuantity = quantityOnHand` for every non-archived variant in scope (all of them for `FULL`, only those whose product matches `categoryId` for `CATEGORY`) in one transaction.
- **`PATCH /stock-takes/:id/lines/:lineId`** — records a count and/or a reason for one line. This *is* T-27's "progress survives interruption": since every count is saved to the server the instant it's entered (not batched client-side), a device dying mid-count loses nothing — the next `GET /stock-takes/:id` picks up exactly where it left off. Recomputes `variance`/`varianceValue` against the frozen snapshot; rejected once the stock take is no longer `IN_PROGRESS`.
- **`GET /stock-takes/:id/discrepancies`** — only lines with a non-zero variance, sorted by `|varianceValue|` descending, exactly matching the doc's review-screen wording.
- **`POST /stock-takes/:id/post`** — rejects first (before any write) if any discrepancy line is missing its required reason. Then, per counted line: lock the variant, compute the real delta against live stock, call `postMovement()` (reason `STOCK_TAKE_ADJUSTMENT`, referencing the stock take) only if that delta is non-zero, and finally flip the stock take to `POSTED` — an uneditable record from then on, per the doc's own "becomes a permanent, uneditable record." One `STOCK_TAKE_POSTED` audit-log entry summarizes every line's before/after/delta.
- **`POST /stock-takes/:id/abandon`** — the schema's existing `ABANDONED` status, finally wired to an endpoint; no ledger writes.
- **`GET /stock-takes`**/**`GET /stock-takes/:id`** — history list and paginated line detail.

**Test suite**: 10 new integration tests — 153 total, stable across two full consecutive runs. One test directly proves the concurrent-sale correctness property: freeze a snapshot, post a real sale that changes live stock, count against what the physical count actually found, post, and assert both the computed delta *and* the final `quantityOnHand` are correct against the live figure, not the stale snapshot.

**Verified live against the real backend and database, reproducing the exact concurrency scenario**: started a real `FULL` stock take against `smoke-owner`'s shop (Rice was at `-7` from earlier offline-sync verification), recorded a count of `3` (`expectedQuantity` correctly frozen at `-7`), then — mid-count, before posting — ran a real `POST /inventory/receive` for 5 units (a legitimate delivery arriving during the count, live stock now `-2`). Posting correctly computed `delta = 3 − (−2) = 5` (not `3 − (−7) = 10`, which is what the naive stale-snapshot bug would have produced), landing final stock at exactly `3` — matching the physical count, with the mid-count delivery correctly preserved rather than silently erased.

**This suite found three real, previously-undiscovered bugs — the entire reason an E2E suite like this earns its keep, and each invisible until now for a specific, traceable reason:**

1. **Every bodyless POST button in the app was silently broken** (stock-take post/abandon, category/supplier archive/restore, purchase-order send/cancel). `apiRequest` (`client.ts`) always sets `Content-Type: application/json`, even on a POST with no body at all. Fastify throws its own well-named `FST_ERR_CTP_EMPTY_JSON_BODY` for exactly that combination, and this app's custom error handler didn't recognize it, downgrading Fastify's own reasonable 400 into a generic 500. **Invisible until now because curl — this project's fallback verification method every time the flaky `browse` tool crashed mid-click — never sends that header without a body**, so months of "verified via curl instead" for exactly these buttons never actually exercised the real client's request shape. Fixed at the root in `app.ts`: a custom `application/json` content-type parser that treats an empty body as `undefined` instead of throwing.
2. **A related, second gap in the same code path**: `error-handler.ts` never checked a caught error's own `.statusCode` — Fastify's *own* malformed-JSON parsing failure (a real, well-formed 400) was *also* being masked as a generic 500. Fixed alongside the first: the handler now returns a genuine error's own 4xx status instead of defaulting to 500 for anything that isn't an `HttpError` or a validation error.
3. **The offline product-search fallback (built in an earlier session, T-21/22) never actually worked under real network-level offline conditions.** TanStack Query's default `networkMode: 'online'` *pauses* a query entirely the moment the browser reports itself offline — it never calls the query function at all, so it never fails, so the `isOffline` detection this component's whole design depends on never became true. This affected **both** the live search query *and* its own offline-fallback query (the fallback reads only the local Dexie cache and touches no network at all, but TanStack Query doesn't know that and paused it too). **Invisible until now because every earlier manual verification of this feature patched `navigator.onLine` directly rather than genuinely blocking the network** — which never triggers `networkMode`'s pausing behavior, since that's driven by the browser's real online/offline state, not just what `navigator.onLine` reports. Fixed with `networkMode: 'always'` on both queries in `ProductSearch.tsx`.

New backend regression test `src/app.test.ts` (2 tests: an empty-body bodyless POST via a real route now succeeds; a genuinely malformed JSON body still correctly 400s) — 172 backend tests total, stable across two full clean runs (a same-session run under heavy concurrent E2E/curl load produced 2 flakes — `search.test.ts`'s already-documented 150ms performance flake, and one `data-export.test.ts` timeout — both confirmed load-induced, not regressions, by re-running clean).

**Verified live, all 5 specs green**: `sale.spec.ts` (search → cart → charge → receipt, cross-checked against a real `GET /sales` and `GET /products` afterward), `refund.spec.ts` (a real restock refund, stock confirmed via API), `receive.spec.ts` (a real PO create→send→receive via the actual `ReceivePurchaseOrderDialog`), `stock-take.spec.ts` (the full start→count→review→post chain with zero discrepancies), `offline.spec.ts` (a real `context.setOffline(true)` charge, a real receipt shown before any server contact, a real automatic drain on reconnect, cross-checked against `GET /sales` afterward — the exact scenario the flaky `browse` tool could never get through cleanly in earlier sessions, now scripted and repeatable).

New `src/modules/notifications/`: `sms-client.ts` (a hand-rolled `fetch` call to Africa's Talking's REST API — no new npm dependency, same bar as the load-test script and CSV exports; sandbox vs. production endpoint keyed off `AFRICASTALKING_USERNAME`; never throws, since a provider outage must never fail the sale/adjustment/till-close that triggered the notification), `notification.service.ts` (`notifyLowStock`, `notifyTillVariance`, `sendDailySummary`, `sendTestSms`, all funneling through one `dispatch()` that checks the phone number, calls `sendSms`, and always writes the `NotificationLog` row), `notifications.routes.ts` (`POST /notifications/test`, `POST /notifications/daily-summary`, `GET /notifications/log`, Manager+Owner).

**The real architectural point, not just a new module**: `postMovement()` (`movement.service.ts`, T-10's shared ledger primitive) now returns a `crossedLowStock` boolean alongside its existing `{movement, variant}` — computed for free from data already in hand (before/after quantity vs. `reorderPoint`, an edge trigger so a variant already sitting below its reorder point doesn't re-alert on every subsequent sale), no extra query. Every real call site that can decrease stock — `sale.service.ts`'s per-line loop, `adjustment.service.ts`, `stock-take.service.ts`'s posting loop — now collects any crossings and fires `notifyLowStock()` **after** its own `$transaction` resolves, deliberately not awaited before the response returns (fire-and-forget, `.catch(() => {})`). This is the same discipline T-16's `SELECT ... FOR UPDATE` concurrency work already established: a slow third-party network call must never happen inside a transaction holding a row lock, and must never add real latency to the 300ms sale-write budget. `till-shift.service.ts`'s existing `closeTillShift()` got the same treatment, firing `notifyTillVariance()` right alongside its pre-existing `TILL_VARIANCE_ALERT` audit-log write.

**Item 4 — no security-headers plugin at all, fixed.** Added `@fastify/helmet` with one deliberate override: `crossOriginResourcePolicy: 'cross-origin'`, replacing helmet's own default (`same-origin`) — that default is meant for a content-serving origin, not an API whose entire job (per item 3's CORS fix, registered immediately before this) is being consumed cross-origin by the frontend; leaving the default would have quietly fought the fix two items ago. **Item 5 — no way to revoke a refresh token / no real logout, fixed.** Refresh tokens used to be purely stateless JWTs, cryptographically valid until their own 30-day expiry with no way to kill one early — "Sign out" only ever cleared client-side `localStorage`. New `RefreshToken` table (id doubles as the JWT's own `jti` claim, `userId`, `expiresAt`, `revokedAt`) — `signRefreshToken` (plugins/auth.ts) now persists a real row per issued token; `POST /auth/refresh` checks that row (not just the JWT's own signature/exp) before minting a new access token; new `POST /auth/logout` (same shape as refresh — no access-token auth required, since the whole point is working even after the access token already expired) revokes the specific row it's given, always `204` even for an already-invalid token (logout isn't a place to leak whether a token was real).

**A deliberate design decision, not an oversight**: this does *not* enforce single-use rotation (revoking the old token every time refresh issues a new one) — reasoned through carefully before building, not discovered by accident. Several components fetching data at once can each hit a 401 around the same moment and race to refresh with the same still-technically-valid token; single-use rotation would make the loser of that race spuriously log the user out, a real regression this fix must not introduce. Multiple simultaneously-valid rows per user is the safer failure mode — the actual property needed is "logout kills a token early," not "a token can only ever be used once." Documented directly on the `RefreshToken` model in `schema.prisma`, not just in a progress note.

**A real bug found wiring this, not before**: `RefreshToken.userId`'s FK defaulted to this schema's usual `Restrict` (protecting business records like sales/audit-log rows from disappearing under their owner) — but a session artifact isn't a business record, and several test files' cleanup hard-deletes their fixture user directly, which started failing the moment a real login during the test actually created a row here to reference. Fixed with a second small migration changing it to `Cascade` — the correct behavior for this table specifically, not a workaround.

Frontend: new `logout()` in `lib/api/auth.ts`; `AppShell.tsx`'s "Sign out" button now calls it best-effort (try/catch — a network failure must never block a user from signing out locally) before clearing `localStorage` and navigating. New `logout.test.ts` (6 tests): a fresh login can refresh; logging out revokes the token and it can no longer refresh even though unexpired; logout is idempotent (twice = two `204`s); a garbage token is a silent no-op; revocation is per-token not per-user (logging out session A leaves session B's own token valid); an access token can't be used to log out (wrong kind, still `204`, doesn't touch the real refresh token from that login). 210/210 full suite (one isolated flake in an unrelated dashboard test reproduced clean alone — this project's well-documented under-load flake pattern, not a regression). Verified live two ways: curl round-trip against the real dev database (login → refresh succeeds → logout → refresh with the *same original* token now `401`s, confirmed directly against the `refresh_token` table showing the login-issued row `revoked_at`-stamped and the rotated row still valid) and a real browser session (clicked "Sign out," confirmed a genuine `POST /api/auth/logout → 204` fired and the app landed back on `/login`).

**Item 6 — localStorage token storage, resolved by decision, not code.** Presented as a real fork (AskUserQuestion, given how different in scope the two paths are): migrate to httpOnly cookies, or document the current approach as an accepted, deliberate tradeoff. `npm audit` reported "No fix available" — true only in the narrow sense that `@prisma/adapter-mariadb@7.9.1` hard-pins `mariadb` to the exact vulnerable `3.4.5` (not a range), so a normal `npm audit fix` can't touch it. A patched `3.5.x` series exists upstream; forcing it via npm's `overrides` field in the root `package.json` is the real fix. Getting `overrides` to actually take effect took real, empirical debugging — worth recording as a lesson: neither reverting `package-lock.json` nor deleting `node_modules` (even together) was enough; npm kept re-resolving `mariadb` back to `3.4.5` regardless, confirmed by checking the lockfile's own `overrides` field stayed `undefined` through several attempts. Isolated the mechanism itself in a throwaway test project first (confirmed `overrides` genuinely works, ruling out a workspace-specific or npm-version bug) before finding the actual fix: **`package-lock.json` itself has to be deleted, not just reverted or left alongside a wiped `node_modules`** — an existing lockfile's already-resolved tree apparently isn't re-evaluated against a newly-added `overrides` entry otherwise, even from a clean install.

**The honest, larger consequence of that fix, not glossed over**: a fully fresh lockfile resolution doesn't just re-resolve the one overridden package — it re-resolves *everything* with any semver flexibility to its current latest-compatible version. 741 package versions shifted (confirmed via the actual diff, not estimated), including an incidental Prisma toolchain bump (7.9.1 → 7.10.0, same `^7.9.1` range in every one of `prisma`/`@prisma/client`/`@prisma/adapter-mariadb`'s `package.json` entries — legitimate, not a mistake, just a real side effect worth naming rather than a targeted single-line fix quietly ballooning without comment). Verified accordingly, not lightly: full backend typecheck, and the complete 210-test suite run twice consecutively clean (one flake in each of two different tests reproduced clean in isolation immediately after — the same system-load pattern this file has documented before, not a regression); frontend typecheck/lint/build all clean; both dev servers restarted on the new dependency tree and a real login against `smoke-owner`'s real account confirmed the whole auth-and-database path still genuinely works end to end with the new driver.

`npm audit` now reports 8 vulnerabilities, down from the original 3 (this project's own prior count) *plus* the newly-found `mariadb` one — the real count went from 4 actionable issues to the same 3 pre-existing, already-assessed ones, with the one genuinely serious, previously-unflagged issue closed.
