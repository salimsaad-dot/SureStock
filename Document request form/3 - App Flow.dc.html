App Flow Document

Screens, navigation, and what happens on every meaningful action.

1. Navigation model

The application has six top-level destinations. On desktop they sit in a persistent left sidebar; on mobile the four most-used appear in a bottom bar with the rest under "More". The active destination is always visible, and the shop name plus sync status sit in the top bar on every screen.

Sell — the point-of-sale screen (default landing for cashiers) Inventory — product list, product detail, receiving, stock takes Sales — transaction history, refunds, till shifts Reports — daily summary, product performance, valuation, shrinkage Purchasing — suppliers, purchase orders, low-stock list Settings — shop profile, staff, categories, tax, devices, backups

Cashiers see only Sell, Inventory (read-only), and Sales (own transactions). Managers see everything except Settings and cost figures. The owner sees all six. Hidden destinations are absent, not disabled — no dead ends.

A global search field, focused with /, finds products, receipts, and suppliers from anywhere. A barcode scanned on any screen jumps to that product; scanned on the Sell screen it adds to the cart instead.

2. Onboarding

First-run setup happens once, on the owner's account, and takes about fifteen minutes plus catalogue entry. Each step is skippable and resumable; a progress checklist stays on the dashboard until it is complete.

  1. Create the account. Owner name, shop name, phone, email, password. Verify by SMS code.
  2. Shop profile. Currency, tax rate and whether prices include tax, opening hours, receipt header and footer text.
  3. Categories. Accept a suggested starter set for the shop type, or write your own. Editable later.
  4. Add products. Two paths: import a spreadsheet (download template → upload → column mapping → validation preview → commit) or add the first product by hand with a guided form. The importer reports each rejected row with a reason and lets it be fixed inline.
  5. Opening stock. Run the first stock take to set real counts and cost prices. Until this is done the dashboard shows an "opening stock not set" banner.
  6. Invite staff. Name, role, and a four-digit PIN. Staff receive an SMS link, set a password, and are ready to sell.
  7. Connect hardware. Test the barcode scanner (a live "scan anything" field confirms input) and print a test receipt.

3. The selling flow

This is the screen staff live in. Layout: a large product search and scan field at the top, a grid of category tiles and favourite products below it, and the running cart on the right (or in a bottom sheet on mobile) showing lines, subtotal, tax, and total.

Action What happens
Scan a barcodeProduct is added to the cart with quantity 1, or its quantity increments if already present. A short tone and a row highlight confirm. Unknown barcode opens a "create this product" prompt for managers, or an error toast for cashiers.
Type in searchResults filter as you type against the local cache, showing name, price, and stock on hand. Enter adds the top result. Out-of-stock items still appear, marked, and can be sold with a confirmation.
Tap a cart lineOpens quantity, line discount, and remove. Discounts above a configured threshold require a manager PIN and a reason.
Hold cartCart is parked with an optional label and the screen clears for the next customer. Held carts appear as chips above the search field.
ChargeOpens payment: method tabs (cash, mobile money, card, account), amount tendered with quick-cash buttons, live change due. Split payment adds a second method row.
Confirm paymentSale is written locally and confirmed immediately, then posted to the server in the background. Success screen shows change due in large type with Print, SMS, and New Sale. New Sale is focused so the flow can continue with one keypress.
OfflineTop bar turns amber: "Offline — N sales queued". Selling continues unchanged. On reconnect the badge counts down to zero and turns green briefly.

Errors: a failed server post never blocks the cashier — the sale stays in the outbox and retries. A sale that the server rejects outright (for example, a deleted product) surfaces in a "needs attention" list for the owner, with the original receipt intact.

4. Inventory flows

4.1 Receiving a delivery

Inventory → Receive stock → choose supplier (or an open purchase order). Scan or search each item, enter quantity and unit cost — the previous cost is pre-filled — and add batch and expiry for perishables. A running total shows units and value received. Saving posts one stock movement per line, updates each product's moving-average cost, marks the purchase order fully or partially received, and shows a summary with an option to print a goods-received note.

4.2 Stock take

Inventory → Stock take → choose full shop or a category. The system freezes an expected-quantity snapshot and presents a count list, optimised for a phone in one hand: item name, a big number field, and next. Counted lines show a live variance. At the end a review screen lists only the discrepancies, sorted by value impact, each requiring a reason before posting. Posting writes adjustment movements and closes the stock take, which then becomes a permanent, uneditable record.

4.3 Product detail

One screen per product: stock on hand, price and cost, margin, a 90-day sales sparkline, days of cover at current velocity, and the full movement history. Actions are Edit, Adjust stock, Reorder, and Discontinue. Discontinuing hides a product from the sell screen without deleting its history — nothing that has ever been sold is deletable.

4.4 Low stock and reordering

Purchasing → Low stock lists every product at or below its reorder point, grouped by supplier, with a suggested quantity. Select items → Create purchase order produces a draft grouped per supplier; each can be sent as PDF or a WhatsApp message and later received against.

5. Sales, refunds, and till shifts

  • History: a reverse-chronological list filterable by date, staff member, and payment method. Tapping a transaction shows the full receipt with its sync status.
  • Refund: open the sale → Refund → select lines and quantities → choose restock or write off as damaged → refund method → confirm. A refund is a new linked transaction with negative amounts; the original is never edited.
  • Open shift: a cashier entering the sell screen with no open shift is asked for the opening cash float.
  • Close shift: the cashier enters counted cash; the system compares against expected, records the variance, and prints a shift summary. Variances beyond a threshold notify the owner.

6. The owner's dashboard

The owner lands on a dashboard, not the till. Top row: today's revenue, transactions, gross profit, and cash in drawer, each with a comparison to the same day last week. Below: a 30-day revenue chart, an attention list (low stock, expiring soon, till variances, failed syncs), and today's top sellers. Every card links straight into the screen that acts on it — the dashboard is a set of doorways, not a wall of numbers.
