Technical Design Document

Stack, architecture, and the reasoning behind each decision.

1. Design constraints

Four constraints drive every choice below. The shop must be able to sell during an internet outage. There is no dedicated operations team, so infrastructure must be nearly maintenance-free. Money is involved, so stock and cash figures must be provably correct rather than eventually correct. And a single developer — or a very small team — has to be able to hold the whole system in their head.

That argues for a boring, well-documented stack over a novel one, a single deployable application over microservices, and a relational database with real transactions over anything looser.

2.1 Alternatives considered

  • A ready-made POS product. Cheaper to start and worth a look, but per-terminal subscriptions, weak offline behaviour, and no control over the data model make it a poor fit for a system you want to shape around your own shop.
  • Firebase / Firestore. Excellent offline sync out of the box, but no multi-row transactional guarantees of the kind stock deduction needs, and reporting queries become expensive and awkward.
  • React Native mobile app. Better hardware access, but doubles the surface area for a shop that mostly sells from one counter. Revisit if barcode scanning by phone camera becomes the primary input.
  • Supabase. A reasonable accelerator — it is Postgres underneath. Chosen against only because the sale write benefits from server-side logic in one place rather than split between database policies and client code.

3. Architecture

Counter PWA ─┐ Phone PWA ─┼─> HTTPS / REST ─> Fastify API ─┬─> PostgreSQL (source of truth) Office web ─┘ (JWT auth) ├─> pg-boss jobs (rollups, alerts) │ └─> R2 object storage (photos, PDFs) └─ IndexedDB cache + offline sale outbox

A single Fastify service exposes the API, organised into modules by domain — catalogue, inventory, sales, purchasing, reporting, admin. Each module owns its routes, its validation schemas, and its service functions; modules talk to each other through service calls, not by reaching into one another's tables. That keeps a future split into separate services possible without forcing it now.

3.1 The sale write

One database transaction does all of the following, or none of it: insert the sale header, insert sale lines with the price and cost captured at that moment, insert one stock movement per line, update each product's cached quantity, and record the payment rows. The transaction takes row locks in product-id order to avoid deadlocks between concurrent tills.

Every sale carries a client-generated UUID. The server treats that UUID as an idempotency key, so a sale replayed by an offline device that never saw the response is stored once, not twice. This single decision is what makes offline sync safe.

3.2 Offline and sync

  • On login the device pulls the full catalogue and caches it in IndexedDB, refreshing by changed-since timestamp afterwards.
  • Offline sales are written to a local outbox with their UUID and a device clock timestamp, and the UI shows a persistent "N sales waiting to sync" indicator.
  • On reconnect the outbox drains oldest-first with exponential backoff. Server time is authoritative for reporting; device time is retained for forensics.
  • Stock may legitimately go negative while offline. The server accepts the sale — it happened — and flags the product for review rather than rejecting reality.
  • Catalogue edits are online-only. This removes the hardest class of merge conflicts entirely.

3.3 Money and rounding

All monetary values are stored as numeric(12,2) in Postgres and handled as integer minor units (pesewas) in application code. Floating point is never used for money. Cost of goods uses a moving weighted average recalculated on each receipt; the cost in effect at the time of a sale is copied onto the sale line so historical margin never shifts when prices change.

5. API surface

REST under /api/v1, JSON in and out, cursor pagination on list endpoints, and errors as a consistent { code, message, details } shape. Request and response bodies are validated with shared Zod schemas.

6. Security, backup, and performance

  • TLS everywhere; passwords hashed with Argon2id; PINs hashed and rate-limited with lockout after repeated failures.
  • Role checks in middleware on every route, with cost and margin fields stripped from responses for roles that cannot see them.
  • Every destructive or financial action writes an audit row: actor, action, entity, before and after values, timestamp, device.
  • Nightly automated database backups with 30-day retention, plus a weekly restore test. A one-click CSV export of all data prevents lock-in.
  • Performance targets: product search returns in under 150ms on a 5,000-SKU catalogue (Postgres trigram index); the sale write completes in under 300ms server-side; the app shell loads in under two seconds on a mid-range Android phone over 3G.
